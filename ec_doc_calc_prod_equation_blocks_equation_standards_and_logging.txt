 Equation Blocks, Equation Standards, and Logging 

 Calculation Blocks 

 Calculation blocks are used to logically group equations and enable iterations over groups of equations. 

 To make it easier to read a calculation, it&#8217;s important to have a standard way of naming calculation blocks. Three important items should be included: 

 A Calculation Index, indicating the position of the block in the calculations 

 A short, meaningful and clear name. Do NOT use Line Breaks as those will break the Calc Log Analyzer tool from working correct. 

 the iterators used. 

 See example below. Level one has no iteration, so only index [20] and short name “Read and pre-process data”. The second level has index [20,20], short name “Read Daily Stream Data” and it iterates over (d=daysInPeriod) and (s=StreamsMeasured). Without the iterator in the name, it&#8217;s impossible to know what we are iterating over when working on equations, so this is really a great help! 

 Although you can have as many equations as you wish inside one block, it is advised not to exceed about 50 equations. The performance of the editor will drop significantly and the overview of what&#8217;s going on will drop. Copy&amp;paste or moving equations may also sometimes fail if you have too many equations, so try to stay below 50. 

 Documentation 

 There are several levels of documentation options and also different option to document your calculation. 

 Equation documentation is the lowest level 

 Should be used when you have a relative complex equation which is hard to understand when looking at the equation. Can also be used to refer to a specification or contract. 

 Should NOT be used to document obvious equations (like the screenshot above). 

 NOTE: Be aware of that the equation documentation is also copied when you copy &amp; paste on equation. There are so many examples of equation documentation not been updated after copy &amp; paste and therefore is not correct anymore. There is a Jira requesting equation documentation NOT to be copied. 

 REMARKS are green lines in between equations 

 Remarks makes the code much easier to read. Should be used to explain what the is the purpose of not only one equation but the next 2-10 equations. Recommend to have at least on REMARK for every calculation block, but more if it makes sense. This is indeed a great help for someone who hasn’t written these equations themselves. 

 Calculation level 

 In the Create Calculation screen, it is important to write something high level about the calculation. It can also be an idea to add a new line which includes your name, date, ticket/description of what is changed. Example below from product calculation EC_MONTHLY_VOLUME 

 Logging 

 There are default three log levels for the screen log. The logs should include the index from the calculation block it is printed from to make it easier to find. 

 No Detail. 

 This is the default and should only print minimum information. This can be agreed with customer. 

 Medium 

 This should also be agreed with customer, what do they want to see. 

 Full 

 This should be a kind of debug level. It can make sense to write to the log using a semi-colon syntax which allows for copy &amp; paste in to excel. In excel user/developer can easily filter and examine details. Example of syntax: 

 INFO = &lt;calc step&gt; ; Node Name ; Stream Name ; PC ; Comp ; Var1 ; Value 1 ; Var2 ; Value2 ; etc 

 In excel, the log will look like this 

 Warning Error and Fatal Logging 

 Agree with the customer what should trigger Warnings in the log. Warnings will not stop the allocation. Missing data which is needed to run a successful allocation must be printed as Errors in the log, but avoid to use Fatal until all data is read as Fatal will terminate immediately. User wants to see a “complete” list of all errors and not one at the time. EC will automatically count number of Errors into ErrorCount (menu - Log messages - ErrorCount). You can test if ErrorCount &gt; 0 at the end of reading input data and make allocation fail using the Log Message “Fatal“ 

 Calculation Equations 

 Equations can be written using many different styles. Using proper equation design is important. The following guidelines ensure correct equation design is used. 

 Generic requirements for equations: 

 Ensure equations are clear and use meaningful variables. 

 Ensure equations in calculations are matching with the calculation design. 
Meaning that the steps and equations provided in the design are implemented in the same hierarchy, details, variable naming and layout. 

 Equations should be logically and clearly organized and grouped. 

 Brackets usage 

 The frequent use of brackets is suggested in all cases, since the use of brackets: make it easier to copy and paste specific parts of equations and more important makes it visible what&#8217;s included in certain arithmetic actions such as for example a Sum function. 

 Example: brackets 

 The equations below seem to be two identical equations. However, one includes both MolFrac and MolWt in the sumation, the other only MolFrac. That cannot be seen without brackets! 

 When brackets are used it shows the equation is wrong. 

 Equation Conditions 

 Make sure you test that a numeric variable is valid and for division by zero to avoid crashing when running the calculation. Try to be structured and only test for isValid() once per object to avoid polluting many equation conditions with isValid() expressions. 

 Remember to use brackets also when writing conditions, it&#8217;s so much easier to read and copy &amp; paste. 

 Equation iterations 

 Equations can iterate over sets. Ensure balance over equation iterations and iterations over entire blocks is properly guarded.
