 Naming Conventions Sets and Iterators 

 Sets and iterators require specific naming conventions. These are discussed in the following sections. It is advised to follow these best practices as closely as possible. 

 Sets 

 EC calculations are heavily using sets to iterate over instead of hardcoding which objects to use. To make it intuitive and easy to read, we must agree on a standard naming convention. By looking at a set, we should know immediately if it is a local set or global set, if it is holding streams, nodes or other assets, if it is a single set only (one row, can be used directly as index without iteration, such as a single component like Methane) and of course how objects in that set are filtered. 

 Many sets can have the same definition across project and customers. To save implementation time and enforce a standardization, we will create template calculations which contains commonly used global set and local sets. Each project can add to the list to cover that project requirements, but should adapt the bellow naming convention. 

 Hierarchical Structure of sets and names 

 Where sets are based on set definitions rather than variables, a hierarchy should be built in order to not repeat the same logic in more than one set definition. 

 Start with a 'base' set at the root of the calculation containing the default set of all objects. 

 Name this base set using the term 'All', such as StreamsAll 

 Create subsets of this set using set operators as required, follow the naming examples and definitions provided further. 

 Global sets 

 Global sets are all sets used in multiple levels of a calculations, which are carried forward between calculation blocks. It is advised to declare these sets on a level as high as possible in the calculation. 

 Global sets are recognizable by their names: 

 Starting with the object(s) held in the set, written fully. Streams, Components, Days etc. 

 Using CamelCase 

 Examples: StreamsAll, ComponentsEmission, DaysInPeriod 

 Date specific sets 

 A number of date specific sets is provided here. It is strongly advised to use these sets as-is. Allowing re-use of calculations. 

 Day &amp; Month Sets 
 Description 

 DaysInPeriod 

 Instead of having a set holding one day and another set holding all days in a month, we create the set DaysInPeriod which is one day if it is daily allocation and all days in the month if it is a monthly allocation. This will be used to read data over DaysInPeriod into non date index variables like gnInitialNStdVol(s). 

 Do not define “d” as a set, “d” is reserved to be used as an iterator. 

 DaysToIterate 

 This will be used to determine if we need to process the network one time or for each day in the month. 

 When it&#8217;s Daily allocation OR Monthly allocation using method 'AGGR_DAYS' then the DaysToIterate is only one day. 

 When it&#8217;s Monthly allocation using mehtod 'LOOP_DAYS' this set will hold all days in the month. 

 Hence, the difference is when we have a monthly allocation using method 'AGGR_DAYS', then DaysInPeriod is all days in the month, while DaysToIterate is only one day. 

 Month 

 This is the toMonth(PeriodStartDate(global)). 

 Do not define “m” as a set which has been done historically, “m” is reserved to be used as an iterator over several months if that is applicable to a calculation. 

 Do not define “d”, “m“, “h“ as a sets, these are reserved to be used as iterators.

 Local sets 

 Local sets are defined on a lower level, like an equation block and serve no purpose outside that block. Using distinct naming conventions and lowerCamelCase. 

 A local set will often use one or more iterators to filter the sets. Examples are p=PhasesUsed or n=NodesASC. Try not to define a local set which is in principle global. E.g. do not add a new set CompC7&#43;, rather make it global. 

 Common local set will be defined in the template to save time and avoid different naming convention. 

 Naming convention 

 start with &lt;four char lowercase object type&gt; 

 Local Stream sets 
 Description

 Set StreamsAll where to_node=n 

 strmOut 
 Set StreamsAll where from_node=n 

 strmInPhase 
 Set strmIn where phase=p 

 strmOutPhase

 Set strmIn where alloc_fixed='Y'

 Dynamic Sets 

 To increase performance and avoid writing 0 to all dimensions on a variable, we can create dynamic sets on-the-fly based on a variable. Create a local variable lsProfitCentresUsed (ls = local set). Then write the equation: lsProfitCentresUsed = args(gnNMass(s, pc in * ), pc) 

 Then, you can later make an iterator pc in lsProfitCentreUsed and you know that only includes those profit centers for that stream which has data. For the next iteration, s, this will be a new list of profit centres for the next stream. 

 Efficient sets are often those based on the underlying data. 

 Use the Args() function in both set definition equations and standard equations to populate a set with those objects that actually exist in the data 

 Only use Args() when you are sure the data has been read from the DB already as Args() will not trigger the reading of out-of-period data 

 Redundant Sets 

 Like local variables, unused sets should be cleaned up from the calculation rules. 

 Object specific sets 

 Object specific sets are sets which are defined to contain a specific (group) of objects, such as streams or nodes.
In general, in order to promote re-usability of calculations, this should be used carefully.
However in specific cases, the use of object specific sets is smart. Such as to prevent unnecessary iterations of large sets. 

 Example: Object specific sets reduce unrequired iterations.

 Which Set Type to Use? 

 Often you have a choice of defining a set either via a set Equation or via the simpler Object Type set combinations. 

 Always prefer the simpler Object Type set combinations rather than an equation in this situation, These are easier to understand for others 

 Remember to utilize the ability to reference sets and iterators as well as fixed constant values. 

 For complex sets you have no choice but to use an equation. In this case remember to enter a description override where appropriate. 

 Beware of Inconsistent Behavior 

 Be aware that calculation engine version idiosyncrasies may mean using a set filter { | } in an equation to populate an indexed set into a local variable sometimes might not work correctly, or may yield a different result from the same syntax used in an explicit set equation. 

 The following such scenario was experienced when populating a set of nomination points: 

 Where the Set Filter is Used 
 How Filter is Used 
 Result 

 Explicit Set Equation 
 Assign the filtered results to a set 
 Correct 

 Regular Equation 
 Assign directly to an indexed Set 
 Incomplete set of points 

 Iteration in Regular Equation 
 Testing by iteration 
 Correct 

 Conclusion: Be aware that evaluation of a set filter in an equation may not be fully supported and may result in incorrect result set 

 Should I always create a set? 

 Only create a set of the collection of elements (such as a subset of delivery points) is used two or more times. 

 If the collection is only used once, then do not create a set. 

 Iterations 

 Iterations are used many times and at many levels. Also iterations must follow a standard to avoid misunderstanding. Many calculations in the past has a set “d” which IS NOT the same as an iterator “d”. This is NOT visible in the editor, so we therefore strongly advice NOT TO define set “d”. (rather use daysInPeriod) 

 You can iterate over a calculation block at multiple levels, you can inside the block iterate over equations and of course you can iterate inside the equation itself. It&#8217;s important to not reuse the same iterator, but inside an equation it is allowed to use the same iterator if it is isolated from the other. 

 This is allowed since the first iterator c3 is only valid inside the brackets and doesn&#8217;t affect the second part.

 Between two and four characters long 

 Lowercase 

 Same values are used across both set names and iterators 

 Consistently applied across all contexts and calculations

 If you iterate multiple times over the same object, like s for stream. Then, let the first iterator be s, the second s2 and so on. 

 Be aware that an iterator used in a set equation will remain in scope for any equation within the block (sub-calculation) in which the set is declared. 

 The value of the iterator will be the last value in the iteration used in the set equation. 

 This could cause problems if you were to accidentally have a reference to the iterator within your equations
