 Calculation Library 

 Introduction 

 Module applicability 

 This module introduces the Calculation Library functionality for EC calculations. 

 Intended audience: 

 Users that already know the basics of the EC calculation framework. 

 Version applicability: 

 The basis for this module is the EC11+ calculation engine. 

 Calculation libraries main principles (1) 

 One or more calculation steps can be extracted to a separate library calculation : 

 The library calculation is maintained independently from the main calculation. 

 The main calculation can «call» the library calculation by using a special step type. 

 Library calculations can be reused. 

 It can be called multiple times from the same calculation. 

 It can be called from different calculations (in the same calculation context). 

 Calculation libraries main principles (2) 

 Library calculations share some data structures with the calling calculation. 

 All global variables are shared. 

 Sets and iterators can be passed from the calling calculation to the library calculation. 

 Local variables can be shared between the calculations, and be used to pass data between them. 

 Library calculations are organized in calculation libraries. 

 Each library can include any number of library calculations. 

 A calculation can call library calculations from different libraries. 

 Library calculations can call other library calculations. 

 Library calculations can call other library calculations, both from the same and other libraries. 

 However, a library calculation cannot call itself, neither directly nor indirectly. 

 Typical use cases for calculation libraries 

 Avoiding multiple instances of commonly used calculations. 

 For example, some calculations apply fairly complex rounding rules at various points in the calculation. 

 Such rounding rules can then be extracted into a library calculation and reused. 

 This reduces maintenance efforts. 

 Using the same calculation steps for different periods. 

 For example, many monthly allocations include running a large part of the daily allocation for each day in the month. 

 The shared part of the daily allocation can then be extracted into a library calculation. 

 The daily allocation «main calculation» is then very simple and mainly consists of a call
to the library calculation which implements most of the actual daily allocation logic. 

 Standardizing calculations across operations. 

 This could e.g. be relevant in a template approach, where parts of the calculation are predefined and other parts are operation specific. 

 The standardized parts could be extracted into library calculations. 

 Maintaining standardized calculations independently of the main calculation. 

 For example, regulatory reporting calculations can be put into a library that is maintained as a separate package. 

 It can be relevant on different levels, e.g. single operations, template approaches and also the EC product itself. 

 How does it work? 

 A simple example 

 Example: 

 The main calculation has three steps, M1, M2, and M3. 

 M3 has two sub-steps, M3.1 and M3.2 

 M2 and M3.1 are both calls to our library calculation. 

 Library calculation has two steps, L1 and L2. 

 Run-time execution flow 

 Example execution flow: 

 If we did not have any library calls, the execution would be: 

 M1 » M2 » M3.1 » M3.2 

 However, M2 and M3.1 are both calls to the library calculation. 

 They are then simply replaced with the library calculation steps L1 and L2. 

 The final execution order is thus: 

 M1 » L1 (from M2) » L2 (from M2) » L1 (from M3.1) » L2 (from M3.1) » M3.2 

 As we can see, the L1 and L2 steps are executed twice, once called from M2 and once called from M3.1 

 The figure above shows the calculation flow. The hatched steps are only
used to organize the calculation and do not contain executable logic. 

 Data scoping for sets, variables, and iterators 

 Variable, set and iterator scope at run time. 

 Works as if there was only one, combined calculation. 

 In the example, this means that e.g. sets defined in M are also available in the library calculation. 

 However, the library calculation is called twice. 

 Each of these calls has a different scope for variables, sets, and iterators, as indicated on the figure! 

 For example, assume the library calculation needs a set called Streams to be «passed» from the caller. 

 If Streams is defined in M then it is available in both calls. 

 Otherwise, it needs to be defined both in M2 and in either M3 or M3.1 to be available in both calls! 

 Note that any global variables etc. are always available in the library calculation. 

 Variable, set and iterator scope at design time. 

 Details of the calling calculation might not be known when writing the library calculation. 

 Library calculations could be called from multiple calculations. 

 Variables and sets expected to be in scope are therefore predefined
when creating the library calculation, and will show up as inherited sets/variables in the screen. 

 The figure above shows merged scope. Variables, sets and iterators
defined along the orange lines are visible to L when it executes. 

 Creating a Library Calculation 

 Creating the calculation library 

 Calculation Library (CO.1060) 

 Standard object create/maintain screen for maintaining calculation libraries. 

 Creating the library calculation 

 Create Library Calculation (CO.1061) 

 Similar to Create Calculation, used to define a library calculation. 

 The Expected Inherited Sets and Expected Inherited Variables 
sections define sets and variables that the library calculation assumes will be in scope at run time. 

 Note that iterators are not predefined (as they are inserted in equations as free text). 

 Editing the library calculation (1) 

 Maintain Library Calculation (CO.1062) 

 Similar to Maintain Calculation, used to build the formulas, etc. for a library calculation. 

 This is exactly the same as Maintain Calculation except for the navigator. 

 Editing the library calculation (2) 

 Maintain Library Calculation (CO.1062) - Inherited sets and variables 

 Sets and variables defined as Expected inherited &#8230;&#8203; in the Create
screen show up as inherited sets/variables. 

 Calling a library calculation from another calculation 

 Adding a "library call" calculation step 

 Add a new library call calculation step: 

 This is done through the context menu just like any other type of calculation step. 

 It is possible to use library calls both for regular steps and decision points. 

 The resulting step can be identified as a library call from the step icon. 

 Selecting the library calculation to call 

 Select "Show library info" from the context menu on the Library calculation step to open the Library tab. 

 Select the library calculation to call from the "Implementing Calculation" dropdown. 

 Shared sets, variables, and iterators 

 Add local sets to be passed on to the library calculation. 

 The exact list of sets is listed in the library call details (or in the Create Library Calculation screen). 

 The sets need to have to be named exactly as expected and be defined in a parent step of the call. 

 The sets cannot be changed by the library calculation; they are only used to pass information to the library calculation. 

 Add local variables to be passed on to the library calculation. 

 The exact list of variables is listed in the library call details (or in the Create Library Calculation screen). 

 The variables need to have the exact same signature as expected and be defined in a parent step of the call. 

 Handle variable values being passed to/from the library calculation. 

 Variables (both global and local) can be resolved and/or assigned by both calculations. 

 This can be used to pass input data to the library calculation, and/or retrieve outputs. 

 In many cases, you might need to prepare or react to these data in steps before or after the library call.
