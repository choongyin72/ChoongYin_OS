### Done wrong / lessons — THE SHARED-KEYWORD REGRESSION (read this in full, do not soften)
**This shared-file change shipped with a real bug on the first attempt, and it broke every other
screen using the keyword, not just a hypothetical edge case.** The PR body originally cited only
the full-tree dryrun (881/881) as the shared-file safety evidence. The reviewer's MUST-FIX gate
rejected that: *"a dryrun never executes the keyword's logic; it proves syntax, not behavior."* This
change didn't just append an optional argument (as PR #555 had done safely) — it **restructured the
loop body** (the column increment moved inside a branch, an index counter was added), which is
exactly the case the project's live-regression-canary rule exists for (mandatory 2+ existing-caller
canaries on every shared-keyword change, no exceptions, per PR #523/#555's own precedent).

The canary run, done as required before merge, found the real defect: **Robot Framework substitutes
`${row2_from}` textually before the boolean IF condition is ever evaluated.** Every existing caller
relies on the empty default `${row2_from}=${EMPTY}`. Textual substitution collapsed the condition
`"${idx} > ${row2_from}"` to the literal string `"1 > "` — invalid Python syntax, **unconditionally**,
for every caller that had never touched the new args. **Area and Meter both failed the canary 0/5**
with `Invalid IF condition ... SyntaxError`. This was not a corner case that only affects unusual
input — it broke the keyword for 100% of its existing callers on the very first live check.

**Fix applied** (same branch, before merge): switched from the string-interpolated `IF` condition to
RF's native-variable syntax (`$var`, no braces) inside a dedicated `Evaluate` call with an explicit
`int()` conversion — avoiding RF's textual pre-substitution trap entirely. The actual fixed logic, as
it stands in `resources/manage_object.resource` today (transcribed verbatim, not paraphrased):

```robotframework
    [Arguments]    ${properties_path}    ${row}=1    ${group}=0    ${start_col}=1
    ...    ${row2_from}=${EMPTY}    ${row2}=1    ${row2_start_col}=1
    ${data}=    Read Properties    ${properties_path}
    ${col}=    Set Variable    ${start_col}
    ${idx}=    Set Variable    ${0}
    FOR    ${label}    IN    @{data.keys()}
        ${idx}=    Evaluate    ${idx} + 1
        ${past_row2_from}=    Evaluate    $row2_from != "" and $idx > int($row2_from)
        IF    ${past_row2_from}
            ${use_row}=    Set Variable    ${row2}
            ${use_col}=    Evaluate    ${row2_start_col} + ${idx} - int($row2_from) - 1
        ELSE
            ${use_row}=    Set Variable    ${row}
            ${use_col}=    Set Variable    ${col}
            ${col}=    Evaluate    ${col} + 1
        END
        ${dd}=    Set Variable    nav:form:G:${group}:R:${use_row}:C:${use_col}:dd
        Select EC Dropdown Option    ${dd}    ${data}[${label}]
        Sleep    0.7s
    END
    Apply Navigator
```

The `$row2_from`/`$idx` (no-brace) syntax inside the `Evaluate` calls is evaluated by Python directly
from RF's variable store, bypassing the textual pre-substitution that broke the original `IF`-based
version.

**Re-canaried after the fix, live:** Area 5/5 PASS, Meter 5/5 PASS, Lifting Account's own suite 5/5
PASS (one unrelated transient locator-click timeout on the first TC01 attempt, clean on immediate
re-run — disclosed, not hidden). Full-tree dryrun re-confirmed 883/883, zero collisions.

**This is one of the most important incidents in this entire backfill project's history** — not
because the regression happened (shared-file changes carry real risk by nature), but because the
canary gate did EXACTLY what it exists to do: caught a defect that a dryrun, a syntax check, and even
the reviewer's own careful hand-trace of the Python short-circuit logic (documented below) all missed,
before it reached master. The reviewer's own follow-up comment states this plainly: *"If I'd merged
on my inspection instead of holding for canaries, every OV-GM suite on master would have broken."*
