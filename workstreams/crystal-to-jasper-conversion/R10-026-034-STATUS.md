## The band-list bug — why R10.030 took so many rounds

`r10_buyergroup.py` moves a report's title AND column header into a `<groupHeader>` so they
repeat per buyer. Every pass in `tmp/` carried its own list of bands to walk, and all of them
predated grouping: `title | columnHeader | detail | summary`. So from the moment R10.030 was
grouped, its **entire header stopped being visited** — by the border passes, the fill passes, the
gap passes, all of them. Each reported "0 changes" and was telling the truth about the bands it
looked at, while the owner kept finding header defect after header defect.

Fixed by `tmp/r10_patch_bands.py`, which inserted a `groupHeader`/`groupFooter` entry into all
seven affected passes. **Any new band type needs the same sweep** — a pass that silently skips a
band is worse than one that fails, because it reports success.

_Why: on 2026-09-05 the chain was allowed to run over the already-verified R10.026 "for
consistency". Three of the four changes were real defects and one was self-inflicted, and the
result was a layout the owner rejected outright: "its totally turn to messy and STUCK report
layout... U can't make assumption the u fixed will apply well to those previous copy report which
had verified OK.. its very dangerous move action". A fix proven on one report does not transfer to
a report that is already correct — a verified report has nothing to gain and everything to lose._

### Two mistakes worth keeping

1. **A rename invalidated the search that followed it.** The row rebuild renamed the number to
   `x="1" width="16"` and then asked for "the first `staticText` on this row" to find the label —
   which returned the number again. The number was moved into the label's slot and the label was
   left truncated. Fixed by identifying the label as the *wide* `staticText`, doing it FIRST, and
   adding a guard that each rebuilt row ends with exactly one number at `x=1 w=16` and one label
   at `x=20 w=245`. The check caught this, which is the point of having one.
2. **`\b` after a closing quote never matches.** `y="360"\b` sits between `"` and a space, both
   non-word, so every cell lookup silently failed — which would have duplicated the cells that
   already existed. The closing quote already makes the match exact; the `\b` was both useless
   and harmful. A guard asserting "every data row has 3 cells" is what surfaced it.
3. **A check that fails for its own reasons is worse than no check.** The first gap check returned
   `None` for the build and read as FAIL, while the build measured 4.0pt against the original's
   4.3pt — a correct result reported as a defect. It invites the "close enough" argument the
   pass/fail design exists to prevent, so the helper was replaced with the measurement that worked.
