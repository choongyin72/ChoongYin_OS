## Mistakes I made this round, and how each was caught

1. **The conditional-red style silently did nothing.** I wrote the JasperReports 6.x nested
   form; JR 7.0.3 accepts the tag and **ignores** it. The report compiled, filled and rendered
   with no red and no warning. Found by checking a working example already in this project —
   R07.012–R07.016 use `<conditionalStyle conditionExpression="..." forecolor="#FF0000"/>`, one
   self-closing element with attributes. Cost two rounds because "the style exists and names the
   right field" was true and still not enough.
2. **A regex bug in eight of my own tools.** `<style name="X"[^>]*(?:/>|>.*?</style>)` returns a
   multi-style **region** for any self-closing style, so cloning duplicated it and JasperReports
   refused **all eight reports** (`Duplicate declaration`). Restored from backup, fixed in every
   file, and added a guard that fails the build on any duplicate style name.
3. **I read three defects off compressed crops that the measurements then contradicted** — a
   caption row and a blank strip "swapping places", a correctly-placed `MMBtu` pair "missing",
   and a 20pt indent that was really leading spaces. A landscape page at 200dpi is 3300px wide
   and gets scaled down until a text line is a few pixels tall. The zoom tool now crops
   horizontally too. **I now use crops for gross structure only and measure anything finer.**
4. **Running the residual refiners after absolute placement made things worse** (R10.034 83% →
   76%): they nudge rows off the positions absolute placement had just got right. Reasserted and
   stopped running them.
5. **Stripping an attribute across a whole style block** also stripped the `forecolor="#FF0000"`
   inside the conditional style. Narrowed to the opening tag.

## Column widths — done for the two reports where it could be done safely

The detail band's column grid was still as authored, because `r10_tablegrid.py` only moves cells
for rows it can locate by matched text and a `detail` cell holds `$F{...}`. Measured on R10.026:

```
build     0..110  110..210  210..285  285..340  340..415  415..470  470..560 ...
original  1..81    81..181   182..262  263..308  309..389  390..425  425..522 ...
```

Every boundary differed, so the data rows did not line up under a header that now matches the
original. `r10_colalign.py` pairs the columns **by index, left to right, and only when the two
counts agree**:

| Report | build cols | original cols | outcome |
|---|---|---|---|
| R10.026 | 10 | 10 | remapped — **74% → 78%** |
| R10.030 ×3 | 14 | 14 | remapped |
| R10.031 ×2 | 17 | **16** | **left alone** |

R10.031's build splits the `Note` area into two columns where the original has one. Pairing 17
onto 16 by proximity would put a value in the wrong column, which is worse than leaving it wide,
so the band is untouched and reported. That needs a decision about which of its columns is
spurious — yours, not mine to guess.
