Common Parameters

Some parameters/ element types are valid for all tag adapters:

Parameter/Element	Value	Comments


config name

	

Unique string

	

Identifier of the configuration. It must be added as EC codes with the type DT_SOURCE_ID.




class (mandatory)

	

<path to implementation>

	

Referring to the class of the adapter.




Sequential (optional)

	

Yes | True OR No | False

	

Indicates if the data coming from the adapter can be expected to be ordered by date/time.




ShiftTimeToPeriodStart (optional) <DEPRECATED, use the attribute in TRANS_TEMPLATE instead>

	

A comma-separated list of source functions

	

For each of the functions listed the timestamp will be moved one period back. This is commonly used if the timestamp is set at the end of a period for a specific function. The parameter will indicate that it should be moved to the start of the period.




DEFAULT_RECORD_STATUS (optional)

	

P | V | A

	

The record status on the values retrieved from the adapter. Valid values are:

P (provisional)

V (verified)

A (approved)

If no value is set the status of the records originating from this adapter will be P. If the value differs from P this must also be changed in the DB; trans_template.overwrite_status must be set to the same value for all affected templates.




RetryTimeout

	

The number of seconds.

	

How many seconds the timeout for the failover mechanism of the adapters should be. Only needed if you plan on using several adapters with the same configuration name for failover.




DateValueFormat

	

A date pattern in Java SimpleDataFormat syntax.

	

The date pattern to use when parsing sample values that are dates in string format. Should be specified when your source datatype is DATE.

To enable the failover mechanism for ECIS adapters, you can create multiple configurations with the same config name. ECIS will then use the first one as the default adapter. If this adapter fails during initialize, ECIS will use the next adapter until there are no more adapters left. If the last specified adapter fails while running, ECIS will fail the schedule and the next schedule that runs will use the next adapter with the same configuration name.

If an adapter fails, ECIS will wait for a timeout. When this timeout occurs the next schedule that runs will use the first adapter once again. If this adapter fails it will proceed to the next adapter in line, etc. How long this timeout should be is specified by the adapter RetryTimeout parameter which can be set as in the example above. This parameter specifies the number of seconds the timeout should be. It is recommended that this timeout is large enough to run many schedules before it occurs.

PI Adapter
Required PI Middleware

To be able to connect to PI, these PI products must be installed on a server:

PI Web API (For PI via REST)

PI OLEDB (For PI via MS SQL Linked Server)

For further information on the PI software requirements, please refer to the documentation from OSISoft.

Source System Configuration

We have four different implementations of the PI adapter. Our recommended solution is to use the REST adapter, which does not require any additional software to be installed. The other recommended adapter is using MS SQL Express server with a database link to PI OLEDB. For historical reasons, we still have a PI JDBC adapter and a PI J-interop adapter, however, we do not recommend using these.

PI via REST

This PI adapter uses the PI Web API to fetch data from a PI server. PI Web API is a RESTful interface to the PI system. It is installed on the PI server and uses HTTPS for communication. No additional software or middleware is required on the client side, making this adapter very simple to use.

Example configuration:

<config name="PI_REST">
    <sourceadapter>
        <class>com.ec.frmw.is.engine.adapter.pi.rest.PiRestAdapter</class>
        <sequential>Yes</sequential>
        <parameters>
            <parameter name="endpointConfig">my-pi-web-service</parameter>
            <parameter name="batchMode">false</parameter>
            <parameter name="maxTagsPerBatch">10</parameter>
            <parameter name="maxParallelRequests">10</parameter>
            <parameter name="maxSamplesPerResponse">10000</parameter>
            <parameter name="statusCheckLatest">true</parameter>
            <parameter name="pctGood">80</parameter>
            <parameter name="avgCalcBasis">TimeWeighted</parameter>
            <parameter name="maxCalcBasis">TimeWeighted</parameter>
            <parameter name="minCalcBasis">TimeWeighted</parameter>
            <parameter name="sumCalcBasis">TimeWeighted</parameter>
        </parameters>
    </sourceadapter>
</config>

Tag Paths and Dynamic Tag Names

The names or IDs of the tags to import data from are configured in the Maintain Mappings screen using the "Tag Id" column. When using the PiRestAdapter the "Tag Id" column supports, in addition to the plain tag name, several other ways of specifying the tag.

Full tag path. This allows looking up the tag without having to search for it by name.

PI AF attribute path or query. Tag names can be stored in attributes on PI AF elements which in turn are referred to via the "Tag Id" column. The adapter will get the tag name from the value of this attribute. This makes it possible to change the tag name dynamically without altering the ECIS configuration.

These additional ways of specifying the tag name require special syntax in the "Tag Id" column.

Tag Path

To get the tag by path, specify the full PI AF tag path in the "Tag ID" column, including the PI dataserver internal name. This is the path to the PI Point of the tag. The path of a PI Point can be found in the PI system or by browsing the PI Web API in a web browser.

The PI dataserver name in the tag path is not the hostname of the server machine. Note also that the path begins with a double-slash and uses a single slash to separate path segments.

Example of a full tag path:

\\MYPISERVER\SINUSOIDU
Dynamic Tag Names

The tag name can be dynamically looked up from the value of a PI AF attribute. In this scenario, the AF attribute must be of string type and the attribute value must be the name of the tag you want to retrieve data from. The PI AF attribute must not have any data references. The PI REST adapter does not support fetching data values directly from PI AF attributes.

There are two ways to specify the PI AF attribute that holds the tag name.

PI AF Attribute Path

To get the tag name from a PI AF attribute path, use the following syntax in the "Tag Id" column, including square brackets:

[P:<path>]

Replace <path> with the full path to the PI AF attribute that holds the tag name.
Path syntax is described in the PI Web API reference.

Example path that gets the tag name from an attribute called "PressureTagName" on an element called "Well1":

[P:\\MySystem\MyDatabase\Wells\Well1|PressureTagName]
The PI AF attribute must be of string type and must not have any data references.
PI AF Attribute Query

To get the tag name from a PI AF attribute query, use the following syntax in the "Tag Id" column, including square brackets:

[Q:<query for element>|<attribute name>]

Replace <query for element> with a query that finds one, and only one, PI AF element.
Replace <attribute name> with the name of an attribute on this element that holds the tag name.
Query syntax is described in the PI Web API query syntax reference.

Example query that gets the tag name from an attribute called "PressureTagName" on an element called "Well1":

[Q:name:Well1|PressureTagName]
The PI AF attribute must be of string type and must not have any data references.

Copy-tag labels can be added after the last square bracket:

[P:\\MySystem\MyDatabase\Wells\Well1|PressureTagName]-COPY-1
[Q:name:Well1|PressureTagName]-COPY-1
Troubleshooting

Requests to the PI Web API can sometimes fail and interpreting the returned error messages is not always easy. This section lists some common error messages and explains what they mean and how to fix the problem.

Please read the EC server and scheduler logs carefully and enable debug logging for additional information and error context.

Some JSON paths did not select any tokens

This error can occur during batch request processing when a parent request did not return expected data used by a child request. It typically occurs when the PI Indexed Search Crawler is not working or the tags have not been indexed. It can also occur when a tag with the given name does not exist in the PI system.

To fix this issue:

Check that the PI Indexed Search Crawler service is running correctly on the PI server.

Check that the spelling of the tag name is correct in the EC Maintain Mappings screen.

Avoid using the PI Indexed Search Crawler by setting the useIndexedSearch adapter param to false or by providing full tag paths instead of just the tag names in the EC Maintain Mappings screen.

Too Many Requests

This error can occur during batch request processing when you exceed the PI server request rate limit. The PI server is simply receiving too many requests too quickly. The sub-requests within a batch counts towards this limit even though they are sent as a single HTTP request from EC. The PI server settings that control the rate limits are called RateLimitMaxRequests and RateLimitDuration. For more information about these settings consult the PI Web API documentation.

To fix this issue:

Reduce the value of the Max Tags Per Batch (maxTagsPerBatch in xml) adapter parameter. There are at least two requests per tag in a batch, but there can be more depending on how the tag name is specified and which source function is used. Take this into consideration when tweaking this value and make sure it is at the very least half the size of RateLimitMaxRequests, preferably quite a bit lower than that.

Reduce the value of the Max Parallel Requests (maxParallelRequests in xml) adapter parameter. Executing batches in parallell speeds up processing but also makes you more likely to hit the rate limit.

Increase the RateLimitMaxRequests setting on the PI server and decrease the RateLimitDuration setting. These are global server settings and might not be desirable to change, but it is an option to consider.

The following ParentIds did not complete successfully

This error can occur during batch request processing when using full tag paths in the EC Maintain Mappings screen and there is something wrong with the given tag path.

To fix this issue:

Check both the spelling of the tag name and that the full tag path is correct. See the Tag Path section for information on how to specify a tag path correctly.

Search source has not yet been crawled

This error can occur during request processing when the PI Indexed Search Crawler is not working or hasn’t indexed the tag.

To fix this issue:

Check that the PI Indexed Search Crawler service is running correctly on the PI server.

Avoid using the PI Indexed Search Crawler by setting the useIndexedSearch adapter param to false or by providing full tag paths instead of just the tag names in the EC Maintain Mappings screen.

Attribute <name> has a data reference

This error occurs when searching for tags using PI AF attribute path or query, and the target attribute has a data reference. The PI Web API does not support getting the value of an attribute that has a data reference. The attribute must be of string type and not have any data references.

To fix this issue:

Use or create a different string-only attribute to hold the tag name.

Remove the data reference from the existing attribute (but make sure this doesn’t break usage of the attribute for other clients).

Note that when using the COMPRESSED source function to fetch interpolated values using the PI REST adapter, the period end time is inclusive. This means a value timestamped at the end of the period (or at the start of the next, incomplete period if you will) is included in the result. This is different from the default behavior of the PI JDBC-based adapters, where the end time is exclusive and this value is not included in the result.
PI via MS SQL Linked Server

Another approach for connecting ECIS to PI is to use MS SQL Linked Server. In this case, the MS SQL Server will act as a bridge between ECIS and PI, thus making it possible to query data using a JDBC connection instead of having to depend on COM or DCOM. Following is an example of how this adapter can be configured:

<config name="PI_SOURCE_1">
    <sourceadapter>
        <class>com.ec.frmw.is.engine.adapter.pi.jdbc.PiJdbcAdapter</class>
        <sequential>Yes</sequential>
        <parameters>
            <parameter name="dbdriver">net.sourceforge.jtds.jdbc.Driver</parameter>
            <parameter name="connecturl">jdbc:jtds:sqlserver://localhost:1433</parameter>
            <parameter name="username">sa </parameter>
            <parameter name="pwd"></parameter>
            <parameter name="linkedserver">PI</parameter>
        </parameters>
    </sourceadapter>
</config>

In the Server Options page set the parameters according to the figure "Server Options page".

You should now be able to connect to PI using the MS SQL Server (JDBC) adapter in ECIS. Please refer to Chapter 8 – MS SQL Server Linked Server in the PI OLEDB Data Provider for the PI System for further information on how to run an MS SQL Server as a Linked Server.

Troubleshooting

In case of problems using this adapter or configuring the MS SQL Server as a Linked Server, try the following:

TCP/IP for SQL Server Express

By default, TCP/IP for SQL Server Express is disabled, so JDBC cannot connect to it and you may get the following exception: Network error IOException: Connection refused: connect

To enable TCP/IP, start the SQL Server Configuration Manager.

Expand SQL Server 2005 Network Configuration node.

In the right pane, select Protocols for SQLEXPRESS. The right pane should now show Protocols and Status columns.

Select Enable from the TCP/IP context menu.

Find or Configure TCP/IP Port

After enabling TCP/IP, you have to find out which port number to use. SQL Server Express allocates a port dynamically each time it is started, so to find or configure the port number, continue using SQL Server Configuration Manager …

Select Properties from the TCP/IP context menu. The TCP/IP Properties dialog should open.

Select the IP Addresses tab.

In the IPAll node …

The TCP Dynamic Ports field shows the currently used port number. If you set that field to blank, then SQL Server Express should not automatically choose another port when it restarts.

Set the desired port number in the TCP Port field.

Press OK to apply your settings and close the dialog.


Test TCP/IP

If you change the TCP/IP port, you have to restart SQL Server Express before it can use the new port number. To test that your port number is used, start a cmd window and type: netstat -an. For instance, if you used port 1433, you should see this line in the list of ports used:

TCP 0.0.0.0:1433 0.0.0.0:0 LISTENING

Authentication Method

By default, SQL Server Express uses Windows Authentication Mode to authenticate connections. If you get this exception: Login failed for user '<User name>'. The user is not associated with a trusted SQL Server connection, then you may have to enable SQL Server Authentication Mode and create or enable a user.

Start Microsoft SQL Server Management Studio Express (SSMSE) and connect to your database server.

In Object Explorer pane, select Properties from your database’s context menu. The Server Properties dialog should open.

Select the Security page.

Select SQL Server and Windows Authentication Mode checkbox.

Press the OK button to close the dialog.

In Object Explorer pane, expand the Security / Logins node.

Select existing user sa. Note that there is a red downward arrow next to that user’s image.

View sa's properties. The Login Properties dialog should open.

Select Status page.

Ensure that the Login: Enabled radio button is selected.

Select the General page.

Enter a password for this user.

Press the OK button to close the dialog.

If you refresh the Object Explorer pane, note that the user sa no longer has a red downward arrow.

PI JDBC
EC is not compatible with PI JDBC Driver 2018 or newer. The reason for this is that EC runs with JVM time zone set to UTC while PI JDBC Driver requires to run the same time zone as PI SQL DAS. For newer versions of EC we recommend using PI Web API instead, while for older versions our adapter with PI via MS SQL Express is a good alternative. See the sections PI via MS SQL Linked Server and PI via REST below for further information. For older versions of the PI JDBC driver, it will still be possible to use it, however one will need to use ECISAgent instead of fetching it through EC directly.

Following is an example of how this adapter can be configured for connecting ECIS to PI using the PI JDBC driver:

<config name="PI_SOURCE_1">
    <sourceadapter>
        <class>com.ec.frmw.is.engine.adapter.pi.jdbc.PiAdapter</class>
        <sequential>Yes</sequential>
        <parameters>
            <parameter name="dbdriver">com.osisoft.jdbc.Driver</parameter>
            <parameter name="connecturl">jdbc:pisql://<PI-DAS-server>; /Data Source=<PI-server>; Integrated Security=SSPI;</parameter>
            <parameter name="username">piadmin</parameter>
            <parameter name="pwd"></parameter>
            <parameter name="timezone">Asia/Singapore</parameter>
            <parameter name="avg_calcbasis">EventWeighted</parameter>
        </parameters>
    </sourceadapter>
</config>

OPC Adapter

OPC stands for Open Platform Communications and is a series of standards for data access and data exchange between industrial systems and devices. EC provides two OPC adapters for importing historical data from OPC servers.

The OPC UA adapter supports the modern OPC Unified Architecture specification.

The OPC Classic adapter supports the older OPC HDA (Historical Data Access) specification.

OPC UA

OPC UA is a platform independent service-oriented architecture that integrates all the functionality of the OPC Classic specifications without the limitations of the mostly Windows specific COM/DCOM technology that OPC Classic is based upon. It is the recommended standard for modern OPC systems.

The EC OPC UA adapter supports only historical data extraction from OPC UA compliant servers.

Tag Mapping

ECIS tag mapping for the OPC UA adapter requires special syntax for the tag id.

Every tag is a node in the OPC UA address space. To uniquely identify a node, each node has an id that consists of a namespace and an identifier. The identifier further consists of a format type and the actual id given in that format. It can e.g. be a numeric value or a string. This information can be found by inspecting the OPC UA server using an OPC UA client application such as UaExpert.

The following string notation is used to define a tag id in the ECIS tag mapping:

<namespace type>=<namespace value>;<identifier type>=<identifier value>

The flags are defined as in the OPC UA XML schema specification. The nsu and p flags are ECIS specific additions to make the tag mapping more human friendly.

The order of the flags is not important in the tag id. The identifier flag can be placed before the namespace flag or vice versa. Values must not contain the semi-colon separator character.

The namespace flags are optional. If a namespace is not provided as part of the tag id the default namespace given by the defaultOpcNamespace adapter parameter is used. When the majority of your tags are located in the same namespace, you can shorten the tag ids by skipping the namespace part and instead provide the namespace using the adapter parameter. If still no namespace is found the adapter falls back to the standard OPC namespace with index 0 (zero).

If the namespace is not given as part of the tag id and the node identifier type is either numeric, string or a path to the node, the identifier type flag can be skipped. It will be automatically deduced from the value.

When provided, these prefixes will be applied to all applicable tag ids. Authentication

The OPC UA adapter supports several authentication methods. Inspect your OPC UA server to determine which authentication methods are enabled on the server. Use the authentication-method endpoint parameter to specify which method the adapter should apply.

The following sub-sections describe the supported authentication methods.

Anonymous

No authentication required. Convenient for testing against OPC UA simulation servers. Do not use this authentication method in production systems.

Basic Username/Password

Authenticate using plain username and password credentials. Use the username and password endpoint parameters to supply the credentials.

Certificate

Authenticate using an X.509 certificate. This authentication method requires a keystore containing the user certificate. See Security for details on how to provide the keystore to the adapter.

The keystore must contain an entry with alias/name userCertificate. The entry must contain a private key and an associated X.509 certificate or certificate chain that identifies the user. If the entry is password protected the password must be equal to the keystore password.

The user certificate has certain field requirements as per the OPC UA specification [Part 6, Section 6.2.3 - User Certificates]. Most notably that the Common Name (CN) attribute of the subject field should be the username. The OPC UA server may have additional requirements for the certificates in the chain.

The user certificate must be registered on the OPC UA server. Consult your OPC UA server documentation for requirements and procedures related to creating and registering user certificates.

Security

It is important to secure the communication between the adapter and the OPC UA server. The adapter supports all OPC UA security modes and policies.

Two endpoint parameters define how security is applied:

security-mode defines whether or not to sign and/or encrypt messages.

security-policy defines which encryption algorithms to use.

Inspect your OPC UA server to see which policies and modes are enabled and available for the endpoint you are connecting to.

In addition to these parameters a keystore file in PKCS12 or JKS format must be provided. This keystore holds certificates and cryptographic keys needed by the applied security mechanisms. The keystore password must be supplied using the keystore-password endpoint parameter.

Which entries the keystore must contain depends on the chosen security and authentication mechanisms. This is described in other sections of the adapter documentation. The following table lists all possible entries.

Alias/name	Description


userCertificate

	

Certificate and private key for user authentication. See Authentication.




clientCertificate

	

Certificate and private key for client authentication, signing and encryption. See Encryption and Trust Management.




serverCertificate

	

Certificate for server authentication. See Trust Management.

Any password protected entries must have a password that is equal to the keystore password.

See Keystore for information on how to create a keystore file.

Encryption

The connection to the OPC UA server can and should be encrypted. When using the HTTPS protocol encryption is handled by SSL/TLS and nothing else is needed. The TCP protocol on the other hand does not have encryption enabled by default and requires configuration to secure the channel.

To enable message encryption for TCP endpoints set the security-mode endpoint parameter to SignAndEncrypt and the security-policy endpoint parameter to anything other than None. Ensure that the security policy you choose is enabled on the OPC UA server.

In addition a keystore must be provided containing an entry with alias/name clientCertificate which contains the client private key and its associated certificate or certificate chain. If the entry is password protected the password must be equal to the keystore password.

The client certificate has certain field requirements as per the OPC UA specification [Part 6, Section 6.2.2 - Application Instance Certificate]. The OPC UA server may not accept the connection if some of the fields do not fulfill the requirements. The OPC UA server may also have additional requirements for the certificates in the chain. Consult your OPC UA server documentation for requirements related to client certificates.

Note especially that the Subject Alt Name (SAN) field must contain the value of the application-uri endpoint parameter. If no value is provided the default application URI is urn:ec:frmw:is:engine:adapter:opc:ua.

If messages should only be signed and not encrypted, set the security-mode adapter parameter to Sign. The client certificate and private key is still required in this case.

Trust Management

The OPC UA server certificate is provided to the adapter automatically when connecting, to be used for securing the communication between the two. But the adapter does not know if the server really is who it expects it to be. To establish trust between the adapter and the server, the server certificate can be provided to the adapter using the keystore. The adapter will then validate the certificate it receives from the server against the provided certificate in the keystore, and only accept the connection if they are equal.

The OPC UA server certificate can be provided to the adapter by adding a keystore entry with alias/name serverCertificate. The entry must contain the server X.509 certificate or certificate chain.

Likewise, the client certificate should be registered on the OPC UA server so that the server can verify the identity of the adapter. Depending on the OPC UA server, the client certificate may either be manually uploaded and registered on the server up front, or you may have to manually enable trust for the client certificate after the first connection. Consult your OPC UA server documentation for how to do this.

Keystore

A keystore file in PKCS12 or JKS format is required when authentication method is set to Certificate or when enabling the various security mechanisms. A keystore file can be created using various tools.

The below example commands use a combination of openssl and keytool. These example commands are intended to serve as a starting point. Do not expect to use them as is. Choose the commands you need and change and adapt them to your specific case. Or use different tools entirely.

The example commands below generate self-signed certificates. This might be fine for test servers, but production servers will require trusted certificates provided by your OPC server admin or your company’s certificate provider. To get a valid certificate for production use, forward the certificate signing request file (.csr) to your certificate provider and they will return a certificate file to you that you can put in the keystore.
User Certificate

To create a keystore containing a self-signed user certificate and key you can use the following commands as a starting point.

First create config files containing parameters used by openssl. Adjust parameter values in these files as needed. In particular, make sure that the commonName is the username, and adjust the other subject parameters to match your company’s location and name.

opcuser.cert.conf
basicConstraints = CA:FALSE

The following commands generate a user private key and certificate and puts them in a keystore file. Adjust arguments as needed. You might want to set a better keystore password than what is used here.

For production servers you should obtain a user certificate signed by a trusted certificate authority (CA) from your certificate provider instead of generating it yourself.
// Generate user private key.
openssl genrsa -out opcuser.key 2048

// Generate user certificate signing request.
openssl req -new -sha256 -key opcuser.key -out opcuser.csr -config opcuser.csr.conf

// Convert CA certificate in DER format to PEM format.
openssl x509 -inform der -in OPCServerCA.der -out OPCServerCA.pem

// Generate signed user certificate (or obtain one from you certificate provider).
openssl x509 -req -days 10000 -in opcuser.csr -CA OPCServerCA.pem -CAkey OPCServerCA.key -CAcreateserial -out opcuser.der -outform DER -extfile opcuser.cert.conf

// Convert user certificate in DER format to PEM format.
openssl x509 -inform der -in opcuser.der -out opcuser.pem

// Generate OPC keystore in PKCS12 format.
openssl pkcs12 -export -in opcuser.pem -inkey opcuser.key -chain -name userCertificate -CAfile OPCServerCA.pem -out opc.p12 -passout pass:energy

Server Certificate

The server certificate is obtained from the OPC UA server. It is not a certificate you generate yourself. You can use the following command to create a keystore holding the server certificate. If you have already created a user or client keystore you can simply import the server certificate directly into that keystore instead of creating a new keystore.

// Generate keystore containing server certificate in PKCS12 format.
keytool -importcert -keystore server.p12 -storepass energy -storetype pkcs12 -file OPCServer.der -alias serverCertificate -noprompt
Combining Multiple Certificates Into a Single Keystore

The above commands generate separate keystore files for each type of certificate. If you need more than one certificate you have to combine these into a single keystore file holding all the certificates. The below commands can be used to achieve that.

First choose one of the existing keystores to import the other keystores into. In the below example commands we will use the user certificate keystore called opc.p12 created previously as the main keystore.

// Import client keystore into opc.p12 keystore.
keytool -importkeystore -srckeystore client.p12 -srcstoretype pkcs12 -srcstorepass energy -destkeystore opc.p12 -deststoretype pkcs12 -deststorepass energy -noprompt

// Import server certificate into opc.p12 keystore.
keytool -importcert -keystore opc.p12 -storepass energy -storetype pkcs12 -alias serverCertificate -file OPCServer.der -noprompt

Troubleshooting

Tips for how to handle various errors that may be encountered during import.

Enable DEBUG log level to print detailed information about the adapter processing in the log.

To print the raw OPC UA server responses to the log for advanced inspection, set the Detailed Log Level on the scheduled job instance to All, or set the ECIS Agent -loglevel parameter to either ALL or TRACE.

When running the import job from the EC scheduler, some OPC UA logging appears in the server log, not in the scheduler log. Set the log level of the org.eclipse.milo logging category to TRACE in the Wildfly admin console to output detailed information about the OPC UA communication in the server log.
Errors

>>>>>>> develop_14.1.x

If you get a connection error saying no endpoint was selected, it means the server doesn’t allow the combination of security-mode and security-policy you have selected in the endpoint configuration. Consult with your OPC UA server administrator what options are available for the server URL you are connecting to.

If data is not imported for some tags and you see error messages saying "message size exceeds configured limit" in the job log, this means the server response is larger than allowed. To solve this issue, either run the import job for a shorter time period, set the value of the Max Samples Per Tag adapter parameter to a non-zero value to enable response chunking, or increase the value of the Max Message Size adapter parameter.

Bad_AggregateConfigurationRejected: If the tags fail with this error code, it means your OPC UA server doesn’t support custom aggregate configuration settings. The adapter customizes the OPC UA aggregate configuration when fetching aggregate samples and you have set the Percent Good Quality (pctGood) adapter parameter to a value other than 100. This error means you cannot use this adapter param because your OPC UA server does not support it. To fix the error remove the Percent Good Quality parameter from your adapter configuration.

Bad_TcpMessageTooLarge: The size of the response message is larger than the current message limits allow. Increase the value of the Max Message Size adapter parameter. The error message might additionally state max chunk count exceeded. The max chunk count is calculated using the formula (Max Message Size / Max Buffer Size) * 2. Take this into consideration when tweaking the message limits.




OPC Classic

OPC Classic is the OPC Foundation’s original set of specifications based on Microsoft Windows technology using COM/DCOM (Distributed Component Object Model) to exchange data between systems.

The EC OPC Classic adapter supports only the HDA part of the specification for extracting historical data.

Required Software and Configuration

The OPC Classic adapter attempts to contact an OPC server over the OPCHDA protocol, hence the OPC server must be OPCHDA 1.0/1.1 compliant and expose the DCOM interfaces with the correct security constraints. The configured user must have COM privileges to launch/activate and access the interface from the node the adapter is running. Further information on how to configure DCOM privileges can be found at http://j-interop.org/quickstart.html.

Note on Server Configuration for Newer Windows Versions
The OPC Classic adapter uses the OPC server’s IP address to connect to it. In newer versions of Windows, SMB by default doesn’t accept connections that use the IP address. To disable this restriction, open the Registry Editor on the server, navigate to HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\LanmanServer\Parameters and add a REG_DWORD value with the name SmbServerNameHardeningLevel, and set the value to 0.

Source System Configuration - Other DBMS/Non-Standard Queries

Since the JDBC adapter produces the select statement in a syntax tailored for Oracle DBMS, there is a possibility to configure the adapter to use predefined SQL instead of the generated. In order for the adapter to inject the needed variables, the SQL should contain keywords for tagId, startDate, and endDate. For aggregated functions, the keyword resolution is also available. The select must also provide the value as the first return column, the timestamp as the second, and an optional quality column as the third. GET_SAMPLES_SQL and GET_LATEST_SQL are mandatory if you want to use the functionality this way. In addition it is possible to specify SQL statements for the following parameters (Source functions in parenthesis): GET_AVG_SQL (AVG), GET_MEAN_SQL (MEAN), GET_MAX_SQL (MAX), GET_MIN_SQL (MIN), GET_SUM_SQL (SUM). If you are using aggregated queries, you will need to use the parameter maxsourceintervalinrequest, and set it to 1. This way the adapter will ask for 1 source interval at a time.

<config name="TAGADAPTER">
    <sourceadapter>
        <class>com.ec.frmw.is.engine.adapter.jdbc.SourceTagJdbcAdapter</class>
        <sequential>Yes</sequential>
        <parameters>
            <parameter name="DRIVER">oracle.jdbc.driver.OracleDriver</parameter>
            <parameter name="DB_URL">jdbc:oracle:thin:@//host:1521/ServiceName</parameter>
            <parameter name="DB_USER">user</parameter>
            <parameter name="DB_PWD">pwd</parameter>
            <parameter name="GET_SAMPLES_SQL">SELECT AVG_WH_TEMP, DAYTIME FROM ECKERNEL_VER_9_4_INC6_01.PWEL_SUB_DAY_STATUS WHERE DATA_CLASS_NAME='$tagId$' AND DAYTIME&gt;to_date('$startDate$', 'yyyy-MM-dd"T"HH24:Mi:SS') AND DAYTIME&lt;to_date('$endDate$', 'yyyy-MM-dd"T"HH24:Mi:SS')</parameter>
            <parameter name="GET_LATEST_SQL">SELECT AVG_WH_TEMP, DAYTIME FROM ECKERNEL_VER_9_4_INC6_01.PWEL_SUB_DAY_STATUS WHERE DATA_CLASS_NAME='$tagId$' AND DAYTIME&lt;to_date('$endDate$', 'yyyy-MM-dd"T"HH24:Mi:SS') AND DAYTIME=(SELECT MAX(DAYTIME) FROM ECKERNEL_VER_9_4_INC6_01.PWEL_SUB_DAY_STATUS WHERE DATA_CLASS_NAME='$tagId$' AND DAYTIME&lt;to_date('$endDate$', 'yyyy-MM-dd"T"HH24:Mi:SS'))</parameter>
        </parameters>
    </sourceadapter>
</config>

Updating the Source After Extraction

It is possible to use the adapter to perform an update on the rows which have been read. If the parameter with name UPDATE_SQL is defined, the adapter will execute this for each row read successfully. The format of this parameter is normal SQL syntax except that you can create markers for where the adapter can insert columns for each row. A marker is of the format $<col_no> where col_no is the index in the select starting from 1.

Example:

<parameter name=" UPDATE_SQL ">update dv_pwel_sub_day_status set status='processed' where somekey=$1 and someOtherKey=$2</parameter>

These update statements are run within the same transaction, so it is possible to have the select statement be a SELECT FOR UPDATE.

Running Multiple SQL Statements to Multiple Target Configurations

If several datasets are fetched from the same connection, you can configure a collection of SourceRowJdbcAdapters. The parameters are the same as described under section Source System Configuration and Supported source functions, but the SQL, update and target parameters are subparameters to a new parameter where the name must contain the string "SRC_TARGET".

 <config name="JDBCADAPTER">
    <sourceadapter>
        <!-- NB: This has changed from previous class SourceJdbcAdapterCollection can execute several SRC_TARGET mappings while SourceRowJdbcAdapter can only execute one sql -->

        <parameters>
            <parameter name="endpointConfig">my-jdbc-endpoint-config</parameter>
            <!-- All sqls target mappings are ordered alphabetically and must contain string 'SRC_TARGET'' -->
            <parameter name="SRC_TARGET_SOME_IDENTIFYING_NAME_1" type="list">
                <subparameter name="SQL">select pa.daytime, pa.avg_wh_press,pa.record_status from parentA pa where pa.lastupdate &gt; to_date('$last_fetch$', 'yyyy-MM-dd"T"HH24:Mi:SS')</subparameter>
                <subparameter name="EcClass">EcClassName</subparameter>
                <subparameter name="Col_1" type="list">
                    <subparameter name="EcClassAttribute">daytime</subparameter>
                    <subparameter name="EcAttributeFunction">package.function</subparameter>
                </subparameter>
                <subparameter name="Col_2" type="list">
                    <subparameter name="EcClassAttribute">avg_wh_press</subparameter>
                </subparameter>
                <subparameter name="Col_3" type="list">
                    <subparameter name="EcClassAttribute">record_status</subparameter>
                </subparameter>
            </parameter>
            <!-- All sqls target mappings are ordered alphabetically and must contain string 'SRC_TARGET'' -->
            <!-- depends attribute indicates that it should not execute if the name inside depends has returned no values -->
            <parameter name="SRC_TARGET_SOME_IDENTIFYING_NAME_2" type="list" depends="SRC_TARGET_SOME_IDENTIFYING_NAME_1">
                <subparameter name="SQL">select ca.daytime, ca.avg_wh_press,ca.record_status from childtA ca  where ca.lastupdate &gt; to_date('$last_fetch$', 'yyyy-MM-dd"T"HH24:Mi:SS')</subparameter>

The configured SRC_TARGET elements will share the database connection but will create independent data units which it will send in sequence for writing to the defined targets. Like the other parameters in the adapter configuration, they are sorted alphabetically. However, this will be overridden by the depends attribute. In the depends attribute it is possible to define one or more SRC_TARGET elements which must return at least one row before the depending SRC_TARGET is executed.

Fetching Data From a Backup Solution

Both the SourceRowJdbcAdapter and the SourceJdbcAdapter collection have the possibility to retrieve data from a failover source. This is achieved by defining the connection parameters inside parameters which name contains "CONNECTION". Like the example below:

 <!-- All connections are ordered alphabetically and must contain string 'CONNECTION' -->
<parameter name="CONNECTION_PROPERTIES" type="list">
    <subparameter name="endpointConfig">my-jdbc-endpoint-config</subparameter>
</parameter>
<!-- All connections are ordered alphabetically and must contain string 'CONNECTION' -->
<parameter name="CONNECTION_PROPERTIES_ALTERNATIVE" type="list">
    <subparameter name="endpointConfig">my-jdbc-endpoint-config-2</subparameter>
</parameter>

Like the other parameters in adapter configuration, they are sorted alphabetically. If the first fails the adapter will try to execute the next. The subparameter ACTIVE_SQL is not mandatory, but if it is present the SQL must return at least one row if the connection should be treated as operational.

Write Row Data to a File

It is possible to write row output to a file. To do that you can use the following parameters:

Parameter name	Value	Comments


CSV_OUTFILE

	

No default value

	

Path to a file where the data is to be written.




CSV_DELIMITER
(optional)

	

;

	

String separating the values in the CSV file. If none is given, a single semicolon is used. If the string is larger than one character, the first character will be appended before the first value and after the last value in each row.




OVERWRITE_OUTFILE
(optional)

	

false

	

If the adapter should always write to the same file this value must be set to true. The default behavior is that for each run it will append a timestamp before the file ending. I.e If CSV_OUTFILE is set to C:\\temp\\csvouttest.txt the adapter will write the results to a file named C:\temp\csvouttest2008-07-09-06-43-37.txt

This functionality works combined with another target system configuration. This means you can add these parameters in combination with writing through a package or directly to an EC Class. The system will then write the rows to a file before sending the DataTransferObjects to the JMS queue. An example of a system using this functionality can look like this:

 <config name="CSVOUT">
    <sourceadapter>
        <class>com.ec.frmw.is.engine.adapter.jdbc.SourceRowJdbcAdapter</class>
        <parameters>
            <parameter name="endpointConfig">my-jdbc-endpoint-config</parameter>
            <parameter name="SQL">select s.daytime, s.avg_wh_press, s.object_id, s.object_code from dv_pwel_sub_day_status s where s.daytime > $last_fetch$</parameter>
            <parameter name="CSV_OUTFILE">C:\\temp\\csvouttest.txt</parameter>
            <parameter name="CSV_DELIMITER">","</parameter>
            <parameter name="OVERWRITE_OUTFILE">true</parameter>
        </parameters>
    </sourceadapter>
</config>
