8. Use GitHub MCP list_pull_requests (state=open) to get ALL open PRs. Print the full list with PR numbers and titles before starting any review -- confirm you have listed every open PR. Then review EACH one (do not skip any):

      - For PC screens: is the parent pre-condition verified (empty parent exists, or baseline-0 member confirmed)?
      - For custom-URL OV: grid-id confirmed by the pre-flight guard (preflight_grid_locator.py), not assumed from a sibling?
      - For event-log screens: is R19 marker oracle used, and is physical delete proven (not just soft-delete)?

      ROBOT FRAMEWORK DESIGN QUALITY -- Is the implementation well-structured?
      - Are T3 keywords reusable (screen-generic) or over-fitted to one test case?
      - Is keyword naming consistent with the existing folder (same verb/noun conventions)?
      - Are test data choices safe: AUTOTEST_ prefix, unique per-run timestamp or code, won't collide with real production data?
      - Does the TC count in the title/body/scorecard/README/SOW all agree with the actual TC count in the .robot file? (R13)
      - Is full I-U-D covered (TC01 clean / TC02 insert / TC03 update / TC04 delete)? A PR that omits UPDATE is incomplete per R26.

      DB ASSERTION QUALITY -- Is the ground-truth check correct and sufficient?

      - For OV/Bank: `Code Should Be Present/Absent In View <correct_view> ${TEST_CODE}` -- correct?
      - For PC/count-delta: `View Count Where Should Be <view> <column> <value> <count>` -- correct?
      - Independent post-run DB re-read explicitly done and result stated (not just "tests passed")?
      - Baseline row count confirmed before the test run (no pre-existing AUTOTEST_ residuals)?

      BETTER ALTERNATIVES -- Could the Worker have done this more simply or robustly?
      - Is there an existing T3 keyword that covers this screen's behaviour and was not reused?
      - Could a generator script (gen_ov_iud_bundle.py or similar) have been used but wasn't -- and would it have prevented a clone error?
      - Is there a simpler selector, a more stable locator, or a less fragile wait strategy than what was used?

      - Would a shared helper keyword (e.g. shared T2) have been a better fit than a new T3-local keyword?

      CLONE QUALITY (for batch/sibling screens) -- Are all tokens correctly substituted?
      - View name, class name, base table, slug, AUTOTEST prefix -- all match THIS screen, not the pilot?
      - Row indices (field positions in the New Object form) independently verified from the recon, not trusted from the exemplar?
      - CHECKLIST.md items reference this screen's artefacts (SOW name, view, base table), not the pilot's?
      - README and SOW prose updated to this screen's specifics?

      SELF-CLEAN RIGOUR -- Is the cleanup truly complete?
      - Physical delete (End Date = Start Date for OV; direct DB delete for event-log) -- not just a UI soft-delete?
      - Residual rows from any earlier failed runs cleaned BEFORE the final live run and confirmed?
      - Existing data (pre-test rows) confirmed untouched after the suite?
