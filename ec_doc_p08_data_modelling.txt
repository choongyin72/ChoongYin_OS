Data Modelling Guideline
Introduction
The main objective of this document is to provide guidelines for the
developer and data model checkers on code standards, best practices and special considerations for an EC system.
EC has a logical data model mainly represented by the class concept with key concepts like Object-, Data- and
Table- classes to represent business objects, data series and configuration. Please read the class documentation
for details in the class model. The rest of these guidelines is focusing on the physical table structure
in the database, but there will be references to the class model. It is important to have the class concept in mind also when designing the physical data model.
General Standards and Concepts
The main approach of data modelling in EC is to create table- and relationship- structures on at least
3NF. There is however exceptions where data have been replicated for performance reasons.
The physical EC data model is semantically rich with broad table structures.
Until recently the tables had a combination of named columns used by the owner, and a set of generic
columns for project additions.
With the introduction of the extension concept, we are gradually phasing out the use of generic columns. Additions should be stored in separate tables linked in the class model as EXTENSION or EXT_JOIN.
Additions with mapping_type=EXTENSION are stored in a narrow table. If there are several/many attributes or relations to be added to a class, these should be gathered in one table. This table should have named columns using EXT_JOIN to link to the main class table. The reason for this recommendation is:
performance to limit the number of joins in the view/report layer.
be aligned with the wide table structure, and the semantics concepts of the existing model.
There can be several reasons why an alternative narrow table and more generic structure could be tempting to consider. But this is a different approach, and the 2 models does not necessarily mix well,
so as a general rule new table structures should follow the wide and semantically rich model.
Code standards
Earlier table and column names in EC should not exceed 24
characters. This was based on Oracles 30 character name limit. Since we often add 3 letter prefix/postfix to the given name, the 24-character rule was important. Even if Oracle no longer have the 30-character limit,
there might be variables in product/project code declared as VARCHAR2(30), so it is still recommended adhering to the 24 character rule. The rule is no longer as absolute as it used to be.
Table and column names must only have uppercase letters with an underscore
separating multiple words. One of the most important tasks in creating tables is to define a good
name for it. This outlines in fact the semantics of the table.
Table name syntax: <subject>_<scope>_<purpose>
When a name is decided, a short documentation of the table must be
provided. The documentation will be implemented as a one-liner using the
COMMENTS command that assigns the text to the table in the database. The
table documentation can be retrieved by the view 'user_tab_columns'. Template for tables can be found in the appendix to this document.

Creating primary keys and unique keys in an EC table
EC has evolved over many years with different best practices for how to define keys on the physical table structures, so there are tables with different patterns in the key structure. In addition, EC has often had tables where the origin and ownership of a row of configuration data could be unclear, this also impact the choice of primary key.
We basically have the following cases in an EC database:
Key type
Example
*Description
Logical
PROSTY_CODES (CODE, CODE_TYPE)
This is the classical case where the PK is the minimum set of data columns that identifies a row. There will in most cases not be a need for an additional Unique key.
Surrogate Global Unique Identifier (GUID)
WELL (OBJECT_ID)
Surrogate keys can sometimes be useful when the minimum set of data columns that identifies a row is complex, or if values in the logical key is likely to change. EC is using this as the PK for object class "singleton" tables. You can probably question if this isolated set is necessary, but it is useful to have a uniform pattern and common code for all object classes. Within each class there is in addition a unique key on code. However, code might not be unique within the physical database table, if several object classes are sharing the same table.
Numeric Surrogate key
SCHEDULE(SCHEDULE_NO)
Before "guaranteed unique" surrogate keys was introduced, it was common to use sequences(counters) to create database unique surrogate keys. EC has several cases of this, typically controlled by a table called ASSIGN_ID. These can give collisions and challenges especially in an upgrade setting, when the same logical record might exist with different surrogate keys, or hard coded sequence numbers don’t match in different databases.
 The recommendation now is to avoid this kind of primary keys, rather use logical keys or GUID’s if special circumstances makes it hard to use logical PK.
Note that almost all EC tables now have a unique REC_ID (GUID), this was introduced in EC 9.4. It might be tempting to use this also as PK, but given the design patterns in EC and especially the upgrade challenges described over, in most cases a logical PK or a combination of object_id and timestamp is preferable.
Consideration around data types
The dominating data types used in EC are:
VARCHAR2
NUMBER
DATE
There are no absolute rules that you should not use other data types, but be careful with Oracle specific
data types and avoid timestamps with time zone. Earlier we have been careful with using binary/large object
data types because they required special handling. This has been improved in newer versions of Oracle, and CLOB/NCLOB
might be good alternatives in some tables.
Date/Timestamp challenge
In EC a lot of our data is linked to date or timestamps. There has been and still are limitations in our support
for several time zones with the same EC database/schema. Please see Time Zone handling in EC (white paper) for a more elaborate discussion
of the challenge. But in a data model setting it is important to know the following:
The column DAYTIME is frequently used (naming standard), but it is not always clear if it represents a date
(production day), or a sub-daily timestamp. It depends on the context, and is especially hard to decide for event based data.
With only supporting one time zone within an ECKERNEL schema this has not been a big problem. But going forward and
wanting to support several time zones, we have to be aware and clearly define if a date column is representing a date or a timestamp.
In tables that stores sub daily data, and where the timestamp is a part of the primary key, the current standard is:
owner reference PK (Typically OBJECT_ID)
DAYTIME      DATE  PK (Timestamp in local time)
SUMMER_TIME  VARCHAR2(1)  PK  (Y/N Need to make current PK Unique for the overlapping hour)
UTC_DAYTIME  DATE (Timestamp in UTC time, currently kept in sync by trigger logic)
PRODUCTION_DAY DATE (The production date the sample belongs to, set by trigger, not necessarily trunc(DAYTIME) )
For now, it is still the local timestamp and summer_time flag that is part of the PK, there is a plan in the future to switch so that UTC_DAYTIME will be used in the PK. Then we can get rid of the SUMMER_TIME flag, and maybe also remove the DAYTIME column, but this requires that report queries and other selects filter first on PRODUCTION_DAY.
There are some open questions on the sequence of the next steps around this. The first step is probably
to make support in the application layer for reading the UTC_DAYTIME column, presenting it in a users local time zone
and writing it back as UTC timestamps to the database. The existing trigger logic should support this already, but
we need to support both types of timestamp references in PK for a while. There is a job to do sorting out the classes where
the definition of what the DAYTIME column represent is unclear. If it is a DATE (production Day), it should not be stored
in UTC and converted on read/write.
Journaling tables
The EC system is doing hydrocarbon accounting, and like all accounting system, traceability and audit login is important.
So when creating new tables, the main rule is that there should also be a corresponding table with the same name + '_JN'.
The exceptions are cases where there is no need for record history, and where the classes on top can not be a part of an interface that would need journaling.
The journal table should have the same columns as the main table, but without the primary key constraint from the main table.

How to do data modelling
EC has some design patterns for organizing the physical data model. This section tries to describe the main principles in the model.
The example tables under refers to the generic terms. When adding new tables and columns in accordance with these patterns, the tables
should be given semantically specific names to make the model easy to understand and relate to.

Data Classes
Description
Transactional data related to an owner object. The data classes are
divided into the following categories:
Transactional data instances appearing on a regularly time stamped
basis.
Event data instances appearing on a variable or irregular time stamped
basis.
Sequence numbered data instances created on a sequential and
time-independent basis.
As described in the Date/Timestamp section, EC has not always been deterministic on what columns with data type DATE
represents. This is especially true for tables used by classes that are defined as event (TIME_SCOPE_CODE='EVENT').
When we now are trying to go towards EC systems that fully support multiple time zones, we need to make sure we
don’t introduce new ambivalent data columns in new tables.
At the same time we are bound by existing naming conventions where certain column name have special meaning and are used in validation, integrity checks etc. Based on this the following guidelines can be given:
When To Use
Data classes are intended as the main storage for transactional data in EC. It requires that the data is owned by an object class and have a date column as part of the primary key. The class model have generic support for row level access, 4 eyes approval etc. related to data classes.

There are other named date columns also frequently used in the EC data model that will not be mentioned explicitly here, but an important distinction for future tables is to separate between dates and timestamps. Timestamps should always have a UTC representation stored.
Table Classes
Description
Table classes was original intended to reflect necessary system tables, typically configuration , access control and entities that did not belong as object classes or data classes.
Through time, it has also been used to hold transactional data that does not fit within the rules for data classes (owner, daytime reference). This has lead to a bit blurry border here, but from a physical data model perspective there are not much to say except that the general guidelines for tables still applies.
There cas also be 3-rd party tables placed inside the ECKERNEL schema that can have table classes put on top of them. Sometimes it might be required with a view in between to meet the class generator requirements.
Constraints and Indexes
All product owned tables in EC should have defined a primary key with an associated index. Usually this index will be named PK_<TABLE_NAME> if it is defined based on the "create table template" further down in this guideline. Note that sometimes after an export/import these indexes can be given a generated index name, and in those cases dropping the primary key can result in a "left behind" unique index. It is important to take this into account when making migration script to change primary keys, otherwise the recreation of a primary key might fail.
Ideally, all foreign keys relations should also be explicitly declared and enforced in the database, but it is not always that easy, since it puts limits on loading sequence for configuration data. An example is class relations where it is hard to have foreign keys because of the way we load class by class alphabetically. It would require restructuring the whole class loading if we need to load all entries in class_cnfg first.
It is important to be aware that the EC product does not attempt to create a complete set of indexes. It is not always given that many indexes gives better performance. There is an overhead in maintaining indexes, and the benefits for queries depends on several factors like number of rows to fetch, selectivity of column values etc. So EC is also depending on project specific analyses and indexes to tune specific systems.
Triggers
An EC system have database triggers on 3 different levels:
On Class level there are what we have called Class Trigger Actions (CTA)
Both generated and hand coded views can have triggers. Typically, these will be "INSTEAD OF TRIGGERS", meaning code that overrides the default DML operation. The EC class layer uses this to a large extent to provide general functionality like row level access, 4 eyes approval and data locking. In addition, the Class trigger action code is included in this kind of triggers.
But in this document we will focus on triggers on the physical tables. This includes different types of table triggers, both generated and hand coded, naming conventions, sharing of responsibility between different layers of trigger etc.
Here is an overview of most common trigger types in an EC database

Under is more details for some of these trigger types.
Insert and update triggers
As described in previous sections of this document, tables in EC contains a set of meta-data columns. Several of these are set in table triggers (or have fallback logic if they are not set by caller application). Here is an example of a generated trigger, notice the naming convention starting with IUG.
CREATE OR REPLACE TRIGGER "IUG_ACCOUNT"
 BEFORE INSERT OR UPDATE ON ACCOUNT
 FOR EACH ROW
 BEGIN
 -- Basis
 IF Inserting THEN
   :new.record_status := nvl(:new.record_status, 'P');
   IF :new.created_by IS NULL THEN
         :new.created_by := COALESCE(SYS_CONTEXT('USERENV'CLIENT_IDENTIFIER'),USER);
      END IF;
      IF :new.created_date IS NULL THEN
         :new.created_date := EcDp_Timestamp.getCurrentSysdate;
      END IF;
      IF :new.rev_no IS NULL THEN
         :new.rev_no := 0;
      END IF;
    ELSE
      IF Nvl(:new.record_status,'P') = Nvl(:old.record_status,'P') THEN
         IF NOT UPDATING('LAST_UPDATED_BY') THEN
            :new.last_updated_by := COALESCE(sys_context('CLIENTCONTEXT', 'USER'),USER);
         END IF;
         IF NOT UPDATING('LAST_UPDATED_DATE') THEN
           :new.last_updated_date := EcDp_Timestamp.getCurrentSysdate;
         END IF;
      END IF;
    END IF;
END;
The generation logic held in PL/SQL package ECDP_GENERATE can create triggers covering the common responsibilities of the Insert and Update operations on a table. Sometimes there is a wish to put more logic into the physical table trigger. Ideally, we would have liked to put the additional logic into separate triggers. Oracle support having several triggers on the same operation, but unfortunately there has been no way to control the sequence of such triggers. Since we often need to control the sequence of steps for a given operation, EC as a general rule only have one Insert/Update trigger for each physical database table.
Until EC 12.2.3, this was done with overwriting the generated trigger that was then named IU_<table_name>. There are basically 3 levels of the IU triggers:
Generated, now named IUG_<table_name>
Common, product owned hand coded, now named IUC_<table_name>
Project specific override, still named IU_<table_name>
The driver behind the change is related to the introduction of Flyway in EC. Since the hand coded triggers are repeatable scripts in Flyway, overrides with the same name does not work well.
Differentiation on name also prevents overriding hand coded triggers in the database by accident when generating new triggers.
In the future we should as much as possible avoid putting project specific trigger code on product owned tables. To achieve this we need to come up with alternative ways to trigger project code, preferable through well-defined API or subscriptions to events.
Generated Product Integrity Control Triggers (PINC triggers)
During Installation of the system or upgrades, the system there is an environment variable called INSTALL_MODE set. In this setting we want to record all configuration changes made to the system. For this purpose there is a set of triggers named AP_<table_name>  (AP=After Pinc). Since it is a bit wage to define what is configuration in EC, the default assumption is that all new tables added to the system is potentially configuration data.
At the same time it is important both for the upgrade performance and to limit the size of the CTRL_PINC table that we don’t log updates on transactional data even when INSTALL_MODE is set.
To control this there is a flag in a table called CTRL_OBJECT that can be used to turn off the generation of AP triggers for tables where it is not needed.
When adding new tables to the EC data model, you need to  decide if you need to make an entry in CTRL_OBJECT and set the PINC_TRIGGER_IND='N'. Be aware that if the table already have an AP-trigger you probably have to remove that trigger manually. The flag only prevents generation of new triggers.
Generated Journal triggers (JN triggers)
The concept of journal tables are described over, but the job of actually copying the rows are done by journal triggers. It is the Class IUD trigger that decides if journaling should take place or not, and increases the rev_no if needed. This is where Journal trigger comes into the picture. For each table where journaling is relevant there is a journal table (<table_name>_JN) and a journal trigger JN_<table_name> that does the actual copying. Notice therefore that if you make changes to a table by adding or removing columns, you need to regenerate the journal trigger. This is done with the package ECDP_GENERATE. You should never manually update the journal trigger.
Packages
The EC systems have a lot of code both system technical and business logic represented in database stored procedures (Oracle PL/SQL). Much of this is organized into PL/SQL packages. Here is an overview of the most common types of packages based on naming conventions.
PL/SQL package naming conventions

Description

Generated packages based on physical table. Typically, used to lookup single values or get entire row based on the primary key.  Will be generated when the EC_PACKAGE flag is set in CTRL_OBJECT. Life cycle management
In a system like EC, database upgrades is one of the main challenges. We are using the tool Flyway that support migration driven database development. Please see the Flyway documentation, and the PL/SQL coding standard for how to write scripts and code, and be aware of the Safe upgrade principle.
An important part here when we do data model changing is migration when the storage structure changes. The guidelines for how this should be done including deprecation management is still work in progress, so please be aware and follow the updates coming in the associated reference material.
